# Workflow de engenharia

## Diagnóstico de carregamento travado

**Incidente de 29/10/2026 — sintaxe inválida no script principal compartilhado:** a versão `1.161.3` tinha um apóstrofo extra em `removeGoogleAdsAutoNotification()` (`String(id||'''')`) no bloco inline de `src/index.template.html`. O navegador rejeita o bloco inteiro durante o parsing; por isso o bootstrap do Hub não executava, nenhuma view era montada e o aviso inicial permanecia em “Carregando base local…”. Com esse HTML, o IndexedDB nem chega a ser aberto: não é lentidão, bloqueio ou corrupção do banco. O selo `v1.161.3` mostrado no print coincide com `VERSION` e `dist/version.txt`, e o mesmo erro estava no `dist/index.html`. O console do navegador e a resposta HTTP do servidor não puderam ser lidos nesta sessão; a causa no artefato `1.161.3` foi confirmada, mas não foi possível verificar quais bytes exatos o navegador recebeu. Corrigimos a aspa e o build agora compila os blocos `<script>` inline da página principal com `node:vm` antes de gerar a distribuição, falhando com caminho e número do bloco se houver erro. Isso protege o shell compartilhado, onde um erro pode deixar várias rotas sem inicialização. Para próximos casos, siga a ordem abaixo e também confira se o build atual foi carregado no navegador.

Em 27/10/2026, a Visão Geral ficou indefinidamente em “Carregando base local…” após a mudança da coluna de ações de campanha. A causa foi um erro de sintaxe em `src/overview/view.js`: faltava fechar uma template string na célula `status`, antes da propriedade `actions`. O navegador recusou o script inteiro (`SyntaxError: Unexpected token 'class'`), portanto `OverviewView` não foi definido. No arranque, `render()` chama `navigation.refresh()` antes de `restoreLocalBase()`; a exceção síncrona seguinte (`ReferenceError: OverviewView is not defined`) interrompeu a execução antes que a leitura IndexedDB começasse. A mensagem de carregamento, que só termina por `ready()` ou `fail()`, ficou presa. Não era lentidão nem corrupção da base.

Ao investigar este sintoma, siga esta ordem:

1. Leia o erro mais antigo no Console e confirme a URL/versão de cache do script. Um erro de parsing pode impedir a definição dos globais que outras views usam.
2. Execute `node --check` no JavaScript de cada arquivo alterado antes do build. O build também valida os scripts inline do shell principal com o parser JavaScript do Node, para que sintaxe inválida impeça a publicação.
3. Inspecione a ordem do arranque: falha síncrona de render não pode impedir o início da recuperação da base nem deixar o estado de carregamento sem saída. O `render()` do shell captura erros, registra-os no Console e exibe toast; a recuperação da base continua pelo fluxo próprio.
4. Depois de corrigir, atualize o query param de cache do script alterado, faça o build e confira o artefato servido. Não apague nem substitua IndexedDB para resolver erro de JavaScript.

Neste incidente, o fechamento ausente foi corrigido e a versão de cache da view foi avançada. Verificação: `node --check src/overview/view.js`; não foi necessário alterar dados ou schema.

## Histórico API que some após atualizar a tela

O IndexedDB (`bases/atual`) é a fonte principal. Uma execução só é “salva” depois que a transação de `saveGoogleAdsDailyCaptures()` termina com sucesso; a prévia não cria histórico. Cada gravação concluída cria uma execução mesmo quando não há diferenças, com contagem de diferenças zero, para registrar que houve uma consulta naquele momento.

**Diagnóstico confirmado em 27/10/2026:** o fluxo de captura atualizava IndexedDB e o estado em memória, mas não atualizava o espelho redundante do histórico depois do commit. Isso deixava a execução dependente somente da base inteira e vulnerável a escritores de base que partissem de uma cópia de aba desatualizada. O estado local atual não prova qual gravação apagou execuções anteriores nem permite reconstruí-las se nenhuma cópia ainda as contém; trate uma aba antiga como risco plausível, não como causa histórica comprovada.

**Falha de apresentação reproduzida em 27/10/2026:** após recarregar a tela, `render()` ocorre primeiro enquanto a base ainda está sendo lida. `google-ads-view.mjs` monta a raiz com um snapshot de histórico vazio e guarda o controller em `mountedRoots`. Quando a leitura da base termina, a nova chamada a `mount()` retornava esse controller existente sem atualizar o histórico recebido; por isso a interface mostrava “Ainda não há gravações” mesmo com a base restaurada (o cabeçalho já mostrava a data da base). A correção sincroniza `google_ads_api_change_history` no caminho de reutilização e renderiza novamente o bloco, sem gravar ou alterar IndexedDB. Ao investigar, se base/data restauradas aparecem mas o histórico fica vazio, verifique primeiro esse ciclo de montagem antes de concluir que os registros foram apagados. Isso corrige a exibição; não reconstrói registros que tenham sido removidos de todas as cópias persistentes.

**Diagnóstico complementar em 28/10/2026:** embora a renderização e o IndexedDB aceitassem até dez execuções, o merge de recuperação `historyForRecovery()` em `src/overview/base-session-cache.js` terminava com `.slice(-2)`. Como essa função também constrói os sidecars após gravação e une as cópias durante recuperação, ela podia conservar só duas execuções para um ciclo posterior de recuperação. O limite agora é obtido de `CampaignDatabase.GOOGLE_ADS_CAPTURE_HISTORY_MAX_ENTRIES` (fallback 24), mantendo base e sidecars alinhados. A retenção foi ampliada para 24 execuções completas. A tela oferece input de 1 a 24, iniciado em 10; ele controla somente a apresentação, não a retenção. A preferência usa `hub:google-ads:change-history-display-limit:v1`. A versão anterior da interface também tinha `records.slice(0, 2)`, corrigida para obedecer ao limite escolhido. Com consulta horária, 24 execuções representam aproximadamente 24 horas monitoradas; suspensão do computador pode alongar o intervalo de relógio. Se houver menos registros do que o limite configurado, aumentar o input não recria execuções já removidas de todas as fontes persistentes.

**Proteções atuais e invariantes para futuras alterações:**

1. Depois do commit IndexedDB, `saveGoogleAdsDailyCaptures()` atualiza o estado da aba e chama `OverviewBaseSessionCache.saveGoogleAdsCaptureHistory()`. Esse sidecar contém exclusivamente `google_ads_api_change_history`, em `localStorage` (compartilhado pelas abas da mesma origem) e `sessionStorage` (da aba). Antes de gravar, mescla as cópias anteriores e a lista nova por ID; para colisões, prevalece a versão com `completedAtUtc` mais recente. Não replique para o sidecar campanhas, Diário, catálogo, Faturamento, tokens ou outros dados.
2. Escritores que substituem `bases/atual`, especialmente `persistLocalBase()`, devem ler o valor atual e mesclar `google_ads_api_change_history` por ID dentro da mesma transação readwrite, antes do `put`. Isso evita que uma aba aberta com estado antigo remova execuções que outra aba já gravou. Invalidar caches ou atualizar a interface não substitui esse merge transacional.
3. Na abertura/recuperação da base, una o histórico do IndexedDB, os sidecars e o histórico encontrado no snapshot geral legado de `sessionStorage`. Use `CampaignDatabase.mergeGoogleAdsCaptureHistory()` e aplique a retenção antes de exibir/persistir. Se o caminho tiver permissão de escrita, persista a união na base; em sincronização somente de leitura, mantenha-a visível no estado em memória. Snapshot legado é fonte apenas do histórico: nunca copie outros campos dele.
4. Retenção: o histórico total guarda no máximo 24 execuções, independentemente de período, origem ou resultado (D0, D−1, manual ou automática, concluída ou falha). A mesma poda é aplicada no IndexedDB, ao unir bases/sidecars e na recuperação de sessão; ao ultrapassar o limite, os registros mais antigos são excluídos das cópias ativas. Execuções sem diferenças também contam. Não crie store ou migração para esse fluxo sem necessidade demonstrada.
5. Se o commit IndexedDB falhar, não confirme a gravação nem crie um registro como se tivesse sido salvo. Se só o sidecar falhar depois do commit, preserve a captura confirmada e avise: a falha do espelho não deve desfazer a base. Se IndexedDB e todas as cópias locais já não tiverem o registro, a aplicação não consegue recuperá-lo; não limpe a base nem restaure um backup inteiro para tentar recuperar somente esse histórico.

Falhas automáticas D0/D−1 que não sejam canceladas pela desativação da rotina ou troca da fonte operacional criam um registro separado no histórico, usando uma transação que altera somente `google_ads_api_change_history`. Marque `status: failed`, mantenha `changes: []` e uma mensagem fixa; não armazene o erro bruto, não crie snapshot e não altere métricas, campanhas, Diário ou Faturamento. A view mostra um cartão vermelho claro identificado como falha e não monta uma tabela de diferenças. Resposta incompleta, dado ausente ou erro continuam cancelando o lote sem normalizar ausências em zero. Falhas não geram notificações de captura concluída.

Ao investigar novo desaparecimento, leia primeiro o erro do Console e o estado de conclusão da transação; compare, em modo somente leitura, `bases/atual`, sidecars da mesma origem e snapshot legado. Rastreie todos os `put` em `bases` para confirmar que mesclam o histórico atual dentro da transação. Confirme a retenção D0 antes de classificar um registro antigo como perda. Não consulte a API Google Ads nem grave dados de campanha durante esse diagnóstico. Os responsáveis atuais são `src/database.js` (entrada, merge por ID e retenção), `src/overview/base-session-cache.js` (espelhos e recuperação) e `src/index.template.html`/`src/google-ads/google-ads-capture-storage.mjs` (ordem de commit, atualização do estado e sincronização dos escritores gerais).

**Retenção e apresentação do histórico:** mantenha no máximo 24 execuções completas no total, sem separar por período, origem ou modo (D0, D−1, janela, manual ou automático). Execuções sem diferenças também contam. Na gravação, recuperação de sessão, merge das abas e abertura do Hub, retenha as 24 execuções mais recentes e exclua as anteriores da base ativa e dos sidecars do histórico. A tela mostra dez por padrão e oferece um input de 1 a 24, com preferência no `localStorage` do perfil (`hub:google-ads:change-history-display-limit:v1`); apresente sempre visíveis e disponíveis para distinguir um limite de tela de registros que já não existem na base. Com a rotina de uma execução por hora, 24 registros cobrem aproximadamente 24 horas de monitoramento ativo, sem garantir uma janela exata de relógio se navegador/computador forem suspensos. Cada execução fica recolhida na tela, identificada por data/hora; gere os detalhes somente quando abrir o item para evitar tabelas ocultas no DOM e preserve o estado aberto durante paginação. Aumentar o limite não recupera registros já excluídos de todas as fontes locais.

## Avisos das capturas automáticas Google Ads

`saveGoogleAdsDailyCaptures()` só é chamado após a captura automática passar pelas validações e o commit IndexedDB terminar. Cada gravação automática concluída de D0 ou D−1 deve emitir um aviso, com ou sem diferenças; uma prévia, erro ou lote incompleto nunca deve avisar como se tivesse sido salvo. Falhas de consulta são registradas separadamente no histórico, sem toast nem detalhes brutos; desativação da rotina e troca da fonte não são registradas como falhas. O toast e o centro persistente `#notificationCenterList` mostram somente `(São Paulo):` seguido do resumo compacto com campanhas que tiveram diferença, campos alterados e contas consultadas; não exibem data, texto de conclusão nem o campo `message` bruto. Notificações antigas sem contagens estruturadas devem derivar esse resumo da mensagem legada, sem voltar a exibir o texto completo.

Os avisos ficam em `hub.google-ads-auto-update:notifications:v1` por até 24 horas (máximo de 20 entradas), e são marcados/entregues individualmente em ordem cronológica. Use o componente dedicado `#googleAdsAutoNotification`, separado do toast genérico: mensagens comuns podem sobrescrever um toast e esconder a confirmação automática. Mantenha o aviso visível por 20 segundos ou até o usuário fechá-lo. Não marque um item como entregue antes de a interface própria ser exibida. A chave `hub.google-ads-auto-update:notification-delivery:v1` serializa o intervalo entre abas; Web Locks protege leitura/marcação e o agendador continua após cada aviso. Se a aba estiver oculta ou sem foco, preserve pendências para entregar ao retornar e também drene após restaurar a base local. Sem acesso a `localStorage`, use fila em memória e mantenha os avisos enquanto a aba atual estiver aberta.

Na investigação, confira separadamente: gravação/registro no histórico, inclusão na fila, foco/visibilidade da aba e substituição do toast. A falha provável corrigida aqui era D−1 e D0 concluírem em sequência: o código anterior juntava as pendências em um único toast de 12 s, mas uma nova publicação podia substituir esse aviso; em outros casos, juntar resumos tornava o texto longo. `#googleAdsAutoUpdateNextExecution` mantém a configuração visual abaixo do rótulo principal; seu tamanho atual (78,125%) é 25% maior que o anterior (62,5%).

### Aprendizado de execução: ajustes de texto com referência visual

Na rodada de 28/10/2026, o retrabalho veio da especificação do texto, não da consulta à API nem do processamento no servidor: a primeira alteração não preservou exatamente o trecho que o usuário havia marcado. A fronteira do texto a manter precisava ter sido convertida em critério de aceite antes da edição.

Para pedidos semelhantes:

1. Transforme a anotação em exemplos literais do resultado esperado, incluindo os casos com e sem diferenças. Para este aviso, o contrato é `(São Paulo): 1 campanha com diferença e 1 campo alterado · 9 contas` e, sem diferenças, `(São Paulo): Sem diferenças · 9 contas`.
2. Localize numa única busca quem compõe a mensagem e todas as superfícies que a exibem: aviso temporário, centro persistente e conversão de notificações antigas. Se compartilham o formatador, corrija essa fonte única em vez de editar cada tela separadamente.
3. Faça uma alteração localizada e confira os consumidores afetados com buscas direcionadas: o texto removido não reaparece e o prefixo e as contagens continuam visíveis.
4. Mantenha o ajuste de microcopy separado de alterações no agendamento, retenção, consulta ou gravação. Não investigue desempenho de rede quando a tarefa for apenas apresentação de texto.
5. Registre o aprendizado nesta referência de engenharia; atualize `docs/maintenance.md` apenas quando um contrato ou responsabilidade do sistema mudar, evitando manter duas explicações detalhadas divergentes.

### Abrir o snapshot a partir da notificação

Cada aviso automático que corresponde a uma gravação concluída carrega o `historyId` exato da execução registrada em `google_ads_api_change_history`. O ícone de detalhamento usa esse ID para navegar até Integrações → Google Ads API e abrir o snapshot correspondente; ele é uma ação separada de “Marcar como lida”. Não derive o registro apenas pelo horário/tipo, não faça outra chamada à API e não renderize detalhes de todos os snapshots antecipadamente. Na entrada da tela, resolva o ID depois que o histórico estiver carregado; crie os detalhes somente para o item solicitado. Se o registro já tiver sido removido pela retenção, informe que não está mais disponível, sem abrir outra execução por aproximação. Esse vínculo por ID mantém a navegação precisa e evita trabalho de consulta/renderização desnecessário.

## Pausa automática por desempenho do produto

A regra por desempenho é opcional e independente da regra por saldo negativo. Para comparações, use os `google_ads_api_capture_snapshots` retidos na base atual e a preferência real `hub:google-ads:capture-snapshot-retention:v1`; o padrão é 10 snapshots automáticos D0/D−1 em conjunto (1–100). O adaptador `overviewTableSnapshot()` passa o limite configurado à regra e o pop-up informa quantos snapshots D0 foram elegíveis até esse teto; não crie um segundo controle de retenção na Visão Geral. A retenção compartilhada inclui D−1, mas a análise de desempenho para pausa usa exclusivamente D0. O botão **Aplicar** persiste a preferência no perfil e poda em transação os snapshots completos excedentes mais antigos; capturas manuais não consomem esse limite configurável e o teto global segue em 100. A retenção do histórico compacto de mudanças é outro contrato. Não consulte métricas do Google Ads de novo para montar a comparação.

Invariantes de disparo e cálculo:

1. A ativação guarda o último ID D0 como baseline e avalia imediatamente os snapshots D0 já retidos; candidatas podem ser pausadas após preflight/status confirmado pela API. Antes de mutar, abre uma confirmação por produto elegível: **OK** prossegue, **Cancelar pausa** ignora esse produto nesta avaliação e o timeout de 10 segundos prossegue automaticamente. Se não houver snapshot, o primeiro D0 completo salvo serve só de baseline. Cada nova avaliação automática exige ID D0 completo diferente, persistido depois da baseline; o botão **Verificar campanhas existentes** reavalia manualmente os snapshots atuais. Redesenhar/abrir a view não basta.
2. A fonte de sinais é o snapshot D0 mais recente e as leituras retidas do mesmo dia local da conta. D0 é acumulado no dia: nunca some totais repetidos nem subtraia D0 de dias diferentes. A janela de desempenho é configurável de 1 a 24 horas (padrão 24), considera timestamps reais e reinicia na virada do dia local da conta; com retenção/cadência menores, a janela observável também é menor. O número de snapshots não representa uma duração fixa.
3. Os critérios da bolinha vermelha e da pausa por produto são configuráveis em conjunto na preferência `hub:google-ads:auto-pause-product-settings:v1` (padrão: exigir bolinha, 2 campanhas ativas, 1 clique por campanha, 100 impressões-alvo e janela de 24 horas; limites: 2–100 campanhas, 1–100.000 cliques, 1–1.000.000 impressões e janela de 1–24 horas). A bolinha usa o Consolidado e a chave `productKey`. Com **Exigir bolinha vermelha** marcado, a pausa requer o mesmo grupo de campanhas que forma o indicador e a captura D0 completa mais recente precisa confirmar todas ENABLED, mapeadas e com métricas completas. Desmarcado, a entrada do grupo usa o mínimo de cliques na última captura D0. Para escolher a vencedora, use snapshots que todas as campanhas elegíveis compartilham dentro da janela; a primeira leitura comum é a linha de base. Cada campanha precisa partir abaixo do alvo e cruzar o acréscimo configurado em uma leitura posterior. Com menos de duas leituras comuns, alvo já atingido na linha de base ou métricas inconsistentes, ignore o grupo; nunca selecione uma vencedora com cobertura parcial. Só decida quando pelo menos duas campanhas cruzaram o alvo: mantenha a que cruzou primeiro e qualquer empate no mesmo snapshot; campanhas sem venda que cruzaram depois podem ser pausadas. Campanhas abaixo do alvo aguardam; campanhas com venda no Diário permanecem protegidas.
4. Toda pausa candidata continua sujeita ao preflight e à leitura do status atual do servidor antes da mutação; não confie apenas no status guardado no browser. A regra só executa com Hub aberto, durante a ativação/verificação manual ou ao receber nova captura. Não altera status/orçamento em dados históricos nem refaz Diário anterior.

Salvar critérios atualiza apenas preferência local e projeção: não executa a pausa. A configuração só muda para o Hub após salvar; não executar nem ativar com rascunho pendente. O marcador vermelho e a regra consultam o mesmo limiar de campanhas/cliques na base consolidada quando o checkbox está marcado. Na revisão, confira separadamente: limite efetivo/pruning dos snapshots, baseline e deduplicação por ID de captura, configuração compartilhada, chave de produto, venda no Diário e status confirmado no servidor. A regra de cálculo fica em `src/overview/view.js`; captura/pruning em `src/database.js`, `src/google-ads/google-ads-capture-storage.mjs` e `src/google-ads/google-ads-view.mjs`; a conexão de snapshot e venda fica em `src/index.template.html`. A explicação da interface e o contrato geral estão em `docs/maintenance.md`.

## Pausa automática por dias sem impressões

A regra usa o campo `zeroImpressionDays` calculado no adaptador `overviewTableSnapshot()` por meio da mesma função `campaignZeroImpressionDays()` da coluna **Dias sem impressões**. A contagem representa dias consecutivos e só avança com registros diários explícitos de zero; lacunas, métricas ausentes e histórico insuficiente interrompem ou invalidam a contagem. O cálculo da automação deve permitir computar a sequência mesmo se o estado local estiver marcado como pausado, pois a elegibilidade é determinada pelo status do inventário mais recente da API (`ENABLED`). Não transforme ausência de histórico em zero.

A preferência separada começa desativada, usa 30 dias, aceita inteiro positivo mínimo 1 sem teto de interface, e aplica comparação inclusiva (`zeroImpressionDays >= days`). A ativação mostra uma prévia e exige confirmação; depois confere também as candidatas existentes. Atualizações completas posteriores reavaliam a regra enquanto a Visão Geral está aberta. Antes de cada pausa, reutilize preflight, validação de vínculo e confirmação de status/permissão do serviço atual; não adicione consulta de métricas à API. Campanhas com venda no Diário não são protegidas por esta regra e isso deve estar claro no modal e na confirmação. Registre o motivo como `campaign_zero_impressions` nos eventos do Diário e aceite-o na lista do histórico.

Alterações apenas de documentação exigem checagem de caminhos/links, coerência com as fontes e rebuild dos metadados uma vez ao fechar a entrega, sem saves ou acesso aos bancos reais. Não execute verificações Git, conforme preferência explícita do usuário.

## Editar, compilar e testar

**Apresentação D0/D−1 é prioridade protegida.** Ao tocar em importação MCC, dados de período, adaptadores ou Visão Geral, mantenha o [contrato prioritário de apresentação](../../../../docs/maintenance.md#contrato-prioritário-de-apresentação-dos-períodos-mcc). Execute `node --test tests/overview-d0-after-d1.test.mjs tests/overview-view.test.mjs tests/overview-mcc-coverage.test.mjs`, build e suíte completa. A regressão deve chegar até o conteúdo renderizado de cartões/tabela: D0 das duas MCCs precisa continuar visível após D−1-only, alternância de períodos e reabertura, sem inventar zero para ausência nem reviver ausência explícita. Falha desse contrato bloqueia entrega; não retire asserts ou recursos para aprovar outra implementação.

Na auditoria de duplicidades históricas, teste a detecção de linhas do manifesto MCC por nome normalizado + conta completa, comparação D−1/D0, conta incompleta sem supressão, preservação das linhas originais e ação reversível na projeção operacional. Divergência posterior das métricas deve devolver todas as linhas à projeção. Use somente dados sintéticos em memória; a varredura não pode consultar/importar MCC real. Rode também `tests/overview-duplicate-audit.test.mjs`, `tests/campaign-ignore.test.mjs` e `tests/overview-view.test.mjs`.

1. Confirme a raiz e preserve mudanças preexistentes sem executar verificações Git.
2. Localize a fonte efetiva antes de editar. Use `apply_patch` para mudanças manuais.
3. Edite fontes canônicas; não altere manualmente cópias geradas em `dist/`.
4. Durante o ciclo, rode somente a regressão ligada à alteração. Para repetir um caso individual, use o filtro nativo do Node:

```powershell
node --test --test-name-pattern='trecho do nome do caso' tests/<modulo>.test.mjs
```

Para regressão de módulo, inclua seus testes de domínio, view/adaptador e contratos protegidos num comando só. No fechamento, avance a versão uma vez, faça o build uma vez e rode a suíte com `node --test --test-skip-pattern='privacy-boundary' --test-concurrency=4`.
