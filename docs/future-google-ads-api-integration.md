# Google Ads API — MVP e evolução

## Estado

**MVP de ações manuais em preparação local (27/10/2026):** a tabela da Visão Geral lista campanhas `ENABLED` e `PAUSED`; oferece **Pausar** (`ENABLED → PAUSED`) ou **Ativar** (`PAUSED → ENABLED`), sempre com confirmação específica. O escopo decidido para a primeira ativação abrange as contas cliente ativas vinculadas às MCCs Nutra e e-com, inclusive contas cliente adicionadas futuramente a essas MCCs. O Hub consulta a capacidade para a conta e MCC selecionadas antes de habilitar a confirmação. Um novo serviço PHP privado expõe somente `capabilities`, `pause_campaign` e `enable_campaign`, usa o mesmo token Bearer/CORS/conta de serviço, monta GAQL fixa por IDs validados e relê o status antes e depois de cada transição. A escrita exige `tracking_google_ads_campaign_writes_enabled => true` e uma allowlist explícita de IDs MCC em `tracking_google_ads_campaign_write_manager_customer_ids`. Antes de liberar, o servidor consulta `customer_client` e confirma vínculo ativo a uma MCC autorizada e que o alvo não é uma conta gerente. Uma MCC futura pode ser acrescentada sem redesign, mas precisa de acesso da conta de serviço e inclusão de seu ID na allowlist. As telas enviadas pelo usuário em 27/10/2026 confirmam nível Padrão para a conta de serviço nas duas MCCs. O endpoint, o wrapper e o pacote de deploy estão somente nos arquivos locais; **nada foi publicado, as chaves de escrita não foram adicionadas à configuração e nenhuma campanha foi modificada**. Portanto, o serviço ainda responde bloqueado. O proxy de leitura existente segue sem métodos de mutação. Ativar muda o status da campanha, mas não garante veiculação.

**MVP de leitura ativo, com comparação de sete dias e projeção operacional prospectiva da API (26/10/2026).** O usuário criou o projeto Google Cloud `Hub Integration`, habilitou a Google Ads API, confirmou nível Explorer, criou a conta de serviço `hub-google-ads-readonly`, concedeu acesso somente leitura às duas MCCs e publicou o proxy PHP e a chave privada na Hostinger. Capturas do Hub enviadas pelo usuário confirmam a carga de 9 contas acessíveis e relatórios para contas das duas MCCs. O comparativo usa o snapshot MCC atual e linhas diárias MCC já armazenadas localmente; linhas mescladas com Excel são excluídas, custo e valor de conversão só comparam quando a moeda coincide, e diferenças numéricas têm destaque visual. Capturas `google_ads_api_daily_captures` podem alimentar leituras operacionais desde 26/10/2026 somente quando a API for ativada no seletor local deste perfil do navegador; **o padrão continua sendo Manifesto MCC**. A preferência não é exportada na base JSON e outro perfil permanece no manifesto sem configuração. A projeção só usa linhas pareadas com MCC, conta e campanha; o Diário MCC salvo e as datas anteriores ficam intactos. Faturamento transacional continua separado. Capturas antigas precisam ser refeitas uma vez para receber o novo vínculo e a taxa da moeda.

**Regra de valor recebida do usuário (26/10/2026):** quando o usuário enviar o novo valor de VPI, aplicá-lo a partir da data de corte da operação. A mudança esperada de VPI não deve ser classificada como erro se os valores necessários estiverem disponíveis para alimentar o sistema. Preservar os valores anteriores à data de corte; o valor exato e o arquivo de origem serão fornecidos depois.

## Objetivo

Usar a Google Ads API como fonte prospectiva das métricas de campanha do Hub, mantendo a importação MCC disponível. A adoção é gradual e opt-in por perfil do navegador: o manifesto MCC é o padrão; cada operador pode selecionar a API apenas no próprio perfil. A projeção da API substitui valores equivalentes por campanha/data somente nas leituras operacionais em memória. Não remove nem regrava o Diário MCC, não migra datas anteriores e não altera vendas, anotações ou dados manuais.

## Cadastro e autorização manual no Google

As instruções do Google mudaram recentemente. **Em 22/10/2026, não seguir tutoriais antigos que mandem solicitar um developer token pela Central de API do Google Ads:** a documentação atual informa que os developer tokens foram descontinuados em 09/09/2026 e que os níveis de acesso agora pertencem ao projeto Google Cloud. A antiga Central de API não é o local para solicitar o acesso novo. Não existe um simples botão “modo desenvolvedor” no Google Ads que, sozinho, libere a integração. Consulte [níveis atuais de acesso](https://developers.google.com/google-ads/api/docs/api-policy/access-levels) e [a transição do developer token](https://developers.google.com/google-ads/api/docs/api-policy/developer-token).

O primeiro MVP usa autenticação de conta de serviço no servidor, sem fluxo de login OAuth do usuário, consent screen, callback local ou client secret no Hub. A API recebe a chave JSON somente do diretório privado do servidor e cria tokens de acesso temporários no backend. O navegador nunca recebe a chave nem o token Google.

**Já realizado pelo usuário:** projeto Cloud dedicado, Google Ads API habilitada, acesso Explorer aprovado e conta de serviço criada; nível **Padrão** foi concedido à conta de serviço nas MCCs Nutra e e-com para ações de campanha. O nível Explorer do projeto continua sendo uma configuração distinta de acesso do usuário, com limite publicado de 2.880 operações por período móvel de 24 horas para chamadas a contas de produção.

**Configuração já feita pelo usuário:** chave JSON instalada em `private-tools/google-ads-credentials/service-account.json`, fora de `public_html`; proxy e wrapper originais publicados. Não enviar a chave por chat nem colocá-la nos arquivos locais do Hub/Tracking MVP. O token compartilhado e a origem local do Hub são reaproveitados; não editar `tracking-config.php` se já contiver essas configurações. As consultas de métricas/configuração e a lista de ações de conversão são operações somente leitura do mesmo serviço PHP privado; uma publicação desse arquivo privado reúne essas operações. O wrapper público permanece igual. A janela móvel de captura D0/D−1 é código local do Hub e não exige outra alteração PHP.

Referências oficiais: [configurar projeto e habilitar API](https://developers.google.com/google-ads/api/docs/oauth/cloud-project), [níveis e limites de acesso](https://developers.google.com/google-ads/api/docs/api-policy/access-levels), [fluxo de conta de serviço](https://developers.google.com/google-ads/api/docs/oauth/service-accounts), [autorização e cabeçalhos](https://developers.google.com/google-ads/api/rest/auth) e [transição/descontinuação do developer token](https://developers.google.com/google-ads/api/docs/api-policy/developer-token).

## Plano técnico proposto

### Fase 1 — consulta somente leitura

- A tela **Integrações → Google Ads API** carrega contas sob demanda, permite selecionar MCC, várias contas dessa MCC e datas e apresenta relatórios agrupados por conta apenas na memória da tela. Ao carregar ou trocar de MCC, todas as contas daquela MCC ficam selecionadas por padrão; as consultas são feitas em sequência.
- O serviço do Hub reutiliza `tracking_hub_api_token`; o proxy PHP aplica CORS por origem, verifica o Bearer e usa o JSON da conta de serviço guardado em `private-tools`.
- Chamadas Google usam `customers:listAccessibleCustomers` e `GoogleAdsService.SearchStream`, com `login-customer-id` da MCC quando necessário. Não há método de mutação, gravação operacional, sincronização automática, upload de conversão ou mudança na Flow.
- O primeiro relatório traz impressões, cliques, CTR, CPC médio, custo, conversões, CPA, valor de conversão e, se aceitas para a consulta, parcelas de impressão na Pesquisa, no topo e no topo absoluto. Consultas têm limite de 366 dias e 1.000 campanhas.
- Versão da API usada pelo proxy: v26. O cabeçalho `developer-token` não é enviado; desde 09/09/2026 os tokens foram descontinuados e o acesso pertence ao projeto Cloud usado pela conta de serviço.

### Fase 2 — consultas de comparação e captura local prospectiva

- **Implementada localmente no Hub:** botão **Prévia diária para comparar**, além de **Consultar desempenho**. O usuário pode executar uma consulta para todas as contas selecionadas dentro da MCC atual. O modo diário de prévia consulta `segments.date`, exibe cada linha por data/campanha em blocos separados por conta/moeda e não grava nem altera a base; para outra MCC, é preciso selecioná-la e repetir a consulta.
- **Comparação diária ampliada localmente:** por padrão, a tela consulta os últimos 7 dias fechados (há atalho para redefinir esse recorte, dentro do limite de 14 dias). A comparação usa o snapshot MCC atual e o Diário local de dias anteriores, pareando por ID completo da conta + MCC + data + nome completo exato da campanha. O Diário só é usado quando a origem é exclusivamente `manifesto`; linhas também mescladas com `excel` são excluídas. O custo histórico é armazenado em BRL e só compara diretamente com conta BRL; nos dias do snapshot usa a moeda original. Diferenças numéricas são destacadas em vermelho. Ausências, nomes duplicados e métricas/moedas sem equivalência seguem como não comparáveis, nunca como zero. O relatório e a comparação continuam apenas em memória de tela.
- A prévia diária aceita até 14 dias e 10.000 linhas por conta; o recorte recomendado para começar são 7 dias completos, com a data final em D−1 ou anterior no fuso da conta. A métrica de parcelas de impressão é opcional se a combinação diária não for aceita.
- **Captura e projeção prospectiva:** a prévia normalizada e os botões de alimentação usam uma janela selecionável de **Hoje** (padrão), últimos 2 dias ou últimos 7 dias, terminando na data local atual de cada conta. Hoje consulta somente D0; escolher 2 dias reconsulta D−1 e D0; 7 dias pode reconsultar até seis dias recentes para refletir atrasos/correções do Google. Somente as datas escolhidas são atualizadas; dias fora da janela permanecem como estavam, e nenhuma seleção pode começar antes do marco 26/10/2026. A gravação valida o dia local antes de salvar e divide a resposta em snapshots por conta/data na propriedade aditiva `google_ads_api_daily_captures`. Não há seletor para atualizar um dia histórico arbitrário. Uma falha em qualquer conta cancela o lote inteiro. D0 recebe a fotografia da configuração atual; quando o dia fecha, essa fotografia só é preservada se tiver sido capturada na própria data, nunca substituída pela configuração de hoje. Sem fotografia daquele dia, status/orçamento/qualificação históricos permanecem ausentes. Zero em dia passado só é inferido para campanha já vinculada em captura completa anterior; sem linhas e sem evidência, mantém cobertura vazia. A cotação cambial de cada dia fica congelada ao ser capturada pela primeira vez. O Diário MCC gravado e o manifesto persistido não são escritos por essa ação.
- **Projeção operacional local:** capturas v2 ou superiores a partir de 26/10/2026 entram numa cópia operacional em memória. O primeiro vínculo exige MCC completa + conta completa + nome exato único; depois, o ID de campanha da API preserva o vínculo interno entre novas capturas, inclusive após uma renomeação. Sem vínculo ou com ambiguidade, a linha não é projetada e o Hub mantém o fallback MCC. Valores presentes da API substituem a célula equivalente na projeção; campos nulos/ausentes preservam o fallback. Nenhum valor é somado entre as fontes. CTR é derivado dos cliques/impressões; parcelas, custo, CPC e valor de conversão mantêm unidades e moeda coerentes. Correções manuais do valor de conversão prevalecem. A API atualiza leituras do Diário, Visão Geral, CPA, Produtos Testados e Controle Macro via projeção, sem gravar seus dados no Diário persistido.
- **Faturamento fica à parte da projeção do Diário:** snapshots API D0/D−1 podem alimentar agregados existentes apenas no perfil com fonte API ativa, usando o mesmo ID campanha/data e respeitando resíduos manuais/correções. D0 é provisório; D−1 aparece como atualizável durante a janela de sete dias. `conversions_value` é o valor de conversão configurado no Google Ads; não comprova comissão ClickBank nem pagamento. Não são criadas vendas individuais nem movimentos de recebimento.
- **Capturas v1:** os registros guardados antes desta alteração continuam como cópia paralela e não são projetados porque não carregam vínculo estável nem taxa USD/BRL congelada. Ao usar esta versão, o usuário precisa clicar novamente em **Alimentar API a partir de hoje** para atualizar as contas que deseja ativar.
- O proxy privado já usado pelo Hub atende `daily_report` e `campaign_config`. A tela GuruMedia também pode solicitar `conversion_actions`, mas a operação só funcionará quando a versão atualizada de `google-ads-readonly-service.php` que a implementa tiver sido entregue pelo fluxo Tracking MVP e publicada em `private-tools`; o wrapper público permanece igual. O código local do Hub não confirma essa publicação. A captura móvel D−1 usa `daily_report` e não exige mudança PHP adicional.
- Executar consultas só para visualização/diagnóstico. Consultar as contas representativas nas duas MCCs em execuções separadas, preferencialmente com volume suficiente, mais de uma moeda, campanhas ativas/pausadas, dias sem métricas e conversões quando houver. Uma falha em uma conta não impede a exibição das outras; custos e valores não são somados entre contas/moedas.

Esta etapa é somente documental: não consultou o Google, não abriu nem gravou a base local e não mudou o servidor. A captura paralela permanece separada e os dados anteriores continuam intactos.

### Passo 2 implementado — projeção prospectiva no Hub (26/10/2026)

- A projeção roda em memória a partir das capturas v2 somente quando **Google Ads API** está selecionada na preferência local deste perfil; o padrão é manifesto MCC e outros perfis não mudam. Ela alimenta a base operacional derivada sem alterar o Diário ou manifesto MCC persistidos.
- As telas derivadas que consomem Diário/snapshots usam a fonte API nas células equivalentes: Visão Geral/cartões, Diário e histórico de campanhas, CPA, Produtos Testados e Controle Macro. O status superior exibe quantas linhas API estão projetadas e quantas ficaram sem vínculo.
- A fonte é selecionada por célula/data, sem soma duplicada. Valor explicitamente retornado (incluindo zero) prevalece; valor nulo/ausente recua para MCC. Captura sem linhas não declara zero. D0/D−1 só recebe sobreposição quando a data do snapshot MCC coincide com a data de conta da captura.
- Capturas USD gravam a taxa USD/BRL que estava ativa no momento da consulta. Custo e valor podem aparecer em moeda BRL equivalente só com moeda BRL ou USD com taxa válida. Outras moedas mantêm MCC como fallback para campos monetários. Correções manuais de valor de conversão são preservadas.
- Capturas normalizadas v4 na janela recente podem alimentar os agregados de conversão do Faturamento quando a fonte API está ativada neste perfil. Mantêm o mesmo ID campanha/data usado pela MCC, moeda original, pagamento e correções manuais. D0 é provisório; D−1 pode ser atualizado durante a janela e não significa pagamento. A MCC continua disponível; datas anteriores a 26/10/2026 não mudam.
- Configuração só fica associada a D0; não atribuir status/orçamento atuais a D−1. Antes de gravar, use **Prévia normalizada** com a janela desejada (Hoje é o padrão), sem gravação ou ativação; confira as contas/linhas e só então clique em **Alimentar API** para o mesmo período.

### Normalização de configuração e agregados — 26/10/2026

- A operação de leitura `campaign_config` consulta campanhas sem segmentação por métricas: inclui pausadas/removidas, status administrativo, `primary_status` e motivos, orçamento identificado por recurso, período e compartilhamento, estratégia e CPA desejado. Estratégias de portfólio usam `accessible_bidding_strategy` com proprietário + ID; portfólio não resolvido é pendência, nunca CPA zero. Limites/truncamento fazem a consulta falhar sem declarar inventário completo.
- **Prévia normalizada** consulta configuração e métricas de cada conta no período selecionado (Hoje por padrão; também há opções de 2 ou 7 dias), valida conta/MCC/moeda/fuso/data e executa o mesmo preparo puro da captura. A comparação principal segue o modelo MCC: compara API com a fonte operacional atual no mesmo recorte e lista apenas linhas com diferença visível em impressões, cliques ou custo. Quando há valor anterior e atual, a tabela mostra o delta assinado; quando a linha não tem registro anterior, mostra `— → valor` para não converter ausência em zero. Linhas sem atividade ou sem par numérico ficam fora da tabela resumida. Diferenças de conversões, status, orçamento, estratégia, qualificação e demais campos ficam sob **Ver impacto completo no sistema**, recolhido e paginado. Campos ausentes mantêm o valor atual; vínculos ambíguos ou fora da projeção não são apresentados como alteração. A prévia não escreve IndexedDB, não muda a fonte operacional e não aciona envio de conversões ao Google. **Alimentar API** faz uma nova consulta somente para o período escolhido; ela grava o resultado consultado naquele momento, que pode ter pequenas diferenças em relação à prévia anterior.
- A captura v4 guarda a configuração observada em D0 e snapshots separados de métricas por dia. Uma linha D0 omitida só recebe zero nos contadores quando a consulta diária informa conclusão completa, o inventário é do mesmo dia e o vínculo com a campanha cadastrada é inequívoco. Em D−1, só uma campanha vinculada por captura anterior pode receber zero numa consulta completa. CTR/CPC/CPA sem denominador e parcelas indisponíveis continuam ausentes. Configuração atual não é reatribuída ao passado; orçamento total não vira orçamento diário e compartilhamento fica identificado. Câmbio de captura D−1 permanece congelado.
- O status atual/qualificação é uma observação de configuração, independente da data do último manifesto. Motivos técnicos ficam preservados. Um motivo de anúncio reprovado numa campanha qualificada não é traduzido como reprovação de toda a campanha.
- Agregados financeiros API usam a janela recente desde a data de corte. A função pura `googleAdsApiBillingSales()` reutiliza as regras existentes de residual manual e correções; a família interna de agregado conserva `source: mcc_conversion_aggregate` por compatibilidade, com `data_source: google_ads_api` e horário de captura explícitos. D0 fica provisório e D−1 atualizável; ambos mantêm pagamento pendente até confirmação explícita. IDs `mcc-conversion:<campanha>:<data>` são compartilhados entre as fontes: substituir contribuição, nunca somar duas vendas.
- `google-ads-capture-storage.mjs` salva snapshots da janela + agregados na mesma transação apenas quando a fonte local é API. No modo MCC, guarda a captura separada e não aplica candidatos API ao Faturamento. Pagamento, movimentos, valores corrigidos e plataforma manual são preservados. Zero sustentado por consulta completa só inativa agregado prévio; não cria venda zerada. A sincronização normal do Faturamento respeita a mesma preferência por perfil.
- Novos módulos: `google-ads-config-domain.js`/`.mjs` (normalização pura), `google-ads-source-preference.js`/`.mjs` (preferência local compartilhada com os adaptadores financeiros) e `google-ads-capture-storage.mjs` (transação). Não há schema/store novo nem publicação automática. Publicar apenas `google-ads-readonly-service.php` na pasta privada já existente.

Referências: [orçamentos e períodos](https://developers.google.com/google-ads/api/fields/v26/campaign_budget), [motivos do status](https://developers.google.com/google-ads/api/reference/rpc/v26/CampaignPrimaryStatusReasonEnum.CampaignPrimaryStatusReason), [estratégias compartilhadas acessíveis](https://developers.google.com/google-ads/api/reference/rpc/v26/AccessibleBiddingStrategy).

### Fase 3 — lacunas de equivalência e contrato de dados

- **Validar no uso real da captura v4:** após a prévia dos sete dias e a primeira gravação, observar as linhas projetadas e sem vínculo nas contas selecionadas das duas MCCs. A projeção requer pareamento MCC + conta + nome exato único na primeira captura; o ID da campanha Google Ads preserva o vínculo em capturas posteriores. Corrigir nomes/ambiguidade na fonte MCC ou manter essas linhas no fallback, sem adivinhar associações.
- **Concluir a comparação monetária:** revisar custo e valor de conversão em dias fechados e na mesma moeda. Para USD, o valor exibido em BRL usa a cotação congelada na captura, então pequenas diferenças frente ao manifesto podem decorrer da cotação; não recalcular histórico com a cotação de hoje.
- **Fusos:** monitorar contas cujo dia local não coincide com o calendário operacional (`America/Sao_Paulo`). A captura é sempre rotulada pela data da própria conta; mudanças de dia durante a chamada cancelam a gravação.
- Validar no servidor publicado a consulta separada de orçamento, estratégia, CPA desejado e qualificação. Ela já está implementada no pacote privado e na prévia, mas a implementação local não comprova publicação nem equivalência real de todas as contas. GEO permanece adiado.
- Inventário/configuração do mesmo dia e consulta diária completa agora permitem normalizar zeros para campanhas previamente vinculadas. Sem esses requisitos, manter ausência de informação; não deduzir remoção, pausa ou zero.
- O status retornado pela API é atual, não histórico diário. Preservar a qualificação MCC e evitar transformar ausência de linha ou status atual em estado histórico.
- Preservar o contrato MCC de D0 parcial, D−1, conflitos e confirmações. A projeção atual só atualiza snapshots de mesma data em memória; a comparação contínua deve detectar correções recentes sem sobrescrever o Diário MCC gravado.
- Faturamento recebe agregados API D0/D−1 somente no perfil API; a janela móvel atualiza até sete dias desde o corte e não regrava Diário/manifesto MCC. Ainda falta evoluir os períodos operacionais para não depender das datas do manifesto e decidir equivalências restantes, sempre preservando a data de corte.
- Manter separadas as anotações, status manuais de Contas, cadastros e demais dados locais que não são métricas diárias de campanha.

Limitações para considerar: relatórios diários segmentados da API cobrem até 37 meses; dados diários mais antigos podem não ser reconstruíveis com a mesma granularidade. Status e configurações atuais também não equivalem automaticamente ao histórico diário observado. Ver [métricas zero e disponibilidade histórica](https://developers.google.com/google-ads/api/docs/reporting/zero-metrics) e [datas/fusos](https://developers.google.com/google-ads/api/docs/query/date-ranges).

### Fase 4 — comparação controlada contínua

Comparar API e MCC lado a lado: cobertura por conta/campanha/data, IDs e nomes, impressões, cliques, conversões, custo original, valor de conversão, moeda, custo convertido, parcelas de impressão, estados, horário/data e diferenças de fechamento D0/D−1. As consultas de comparação de dias fechados não escrevem. As capturas do dia atual podem aparecer na projeção operacional em memória, mas não reescrevem dados MCC persistidos nem datas anteriores. Registrar divergências e sua causa; não corrigir ou sobrescrever o Diário MCC automaticamente. A saída desta fase é manter, ajustar ou expandir a projeção conforme a qualidade observada.

Critérios mínimos para avançar:

- nenhuma duplicação nem divisão de histórico;
- equivalência compreendida para métricas e moedas nas datas/contas de teste;
- reconciliação segura de linhas omitidas e dias com zero;
- datas estáveis em contas com fusos relevantes;
- conflitos preservados para decisão explícita;
- acesso da conta de serviço revogável, chave protegida fora de `public_html` e modo de falha compreensível;
- importação MCC disponível como fallback durante o piloto.

### Fase 5 — extensão da projeção após validação

Configuração atual, zeros com evidência e fechamento D−1 recente têm caminho v4. A próxima extensão deve cobrir o avanço dos períodos operacionais sem depender das datas do manifesto, antes da adoção exclusiva da API. GEO continua opcional/adiado. Manter a importação MCC disponível no perfil de outros operadores e para fechamento/validação. Qualquer gravação física no Diário, backfill além da janela ou retirada da MCC exige uma decisão separada.

## Pendências para ativação e comparação

- A comparação inicial de sete dias fechados foi usada para a decisão de adoção prospectiva. Para a continuidade, conferir a prévia em contas com atividade nas duas MCCs, garantindo que o Diário MCC já tenha sido importado e que as linhas comparadas não estejam mescladas com Excel. Tratar apenas o estado **Diferença** como divergência numérica; **Sem par MCC** e **Sem linha API** são lacunas de pareamento/cobertura.
- Após reexecutar a captura v2, conferir no status do Hub as linhas projetadas e as sem vínculo; então observar a projeção nas telas durante alguns dias. Ajustar qualquer campanha marcada sem vínculo antes de confiar no conjunto completo. O Faturamento requer decisão e modelagem à parte.

## Opção futura: executar sem a Hostinger

A integração pode migrar para um pequeno backend local no mesmo computador do Hub, iniciado junto com ele. O navegador continuaria chamando um serviço de loopback, e a chave ficaria fora dos arquivos do Hub e do diretório publicado. Isso elimina o provedor externo para este fluxo, mas limita as consultas à máquina ligada e ao serviço local em execução. Não colocar a chave no JavaScript, `dist`, `localStorage` ou no repositório. Esta alternativa fica registrada para uma etapa futura; a execução atual continua usando o proxy da Hostinger.

## Diretório local e captura em lote de todas as contas

A tela mantém o diretório de MCCs e contas cliente no `localStorage` do perfil/origem do Hub, pela chave `hub.google-ads-account-directory:v1`. O diretório não contém token nem dados de campanha. Reabrir a tela carrega a lista local sem fazer outra consulta de acesso; **Atualizar lista de MCCs e contas** substitui essa fotografia quando os acessos mudarem. O diretório é isolado por perfil do navegador.

**Alimentar todas as contas** percorre os clientes presentes na lista local, consulta métricas diárias e configuração atual em cada conta e grava somente a janela selecionada (Hoje por padrão) em uma única transação local. Na primeira execução, sem diretório salvo, a própria ação consulta a lista antes de capturar. MCCs são agrupadoras de acesso e não são consultadas como se fossem contas de campanha. Avisos de acesso bloqueiam a captura em lote até revisão; qualquer falha numa conta também impede a gravação parcial do lote, com mensagem para correção e nova tentativa. Os relatórios permanecem separados por conta/moeda e a preferência de fonte continua sendo local por perfil. Essa ação não altera campanhas, não envia conversões ao Google e não requer deploy do serviço privado.
